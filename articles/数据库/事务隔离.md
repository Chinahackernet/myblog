在日常工作中，经常听到事务，那什么是事务呢？

​  

我们以一个转账的例子来说明，现在有A和B两个人，他们银行卡里分别有100元和0元，现在A要向B转50元，我们期待的结果是：在转完帐后A的银行卡还有50元，B的银行卡也有50元。具体的过程如下：

1.  从A银行卡查询余额——100元
2.  在A银行卡做扣除操作——100元-50元=50元
3.  更新A的银行卡余额——50元
4.  从B银行卡查询余额——0元
5.  在B银行卡做增加操作——0元+50元=50元
6.  更新B的银行卡余额——50元
7.  完成所有操作

​  

从逻辑上看，整个过程遵守顺序执行就没问题。但是，如果在执行第3步之后数据库宕机，就会出现一个严重的后果：A上的钱已经减少了，但是B上的钱并没有增加。这就导致了数据丢失——我的钱飞了。

​  

为了解决这种问题，数据库就引入了事务的概念——旨在保障数据操作要么全部成功，要么全部失败。

​  

在MySQL中，事务支撑是存储引擎实现的。在前面的文章提高过，MySQL是一个多存储引擎系统，但是并不是所有存储引擎都支持事务，比如MyISAM就不支持事务，这也是它被InnoDB取代的原因之一。

​  

今天这篇文章将以MySQL的InnoDB为例，来对事务进行展开阐述。

​  

## 什么是事务，它的特性有哪些？

事务是指一系列操作被视为单个不可分割的逻辑工作单位，这些操作要么全部执行成功，要么全部失败回滚。在数据库管理系统中，事务通常用来保证数据的一致性和完整性。

  
要实现事务，就需要满足以下特性：

-   原子性（Atomicity）：一个事务的所有操作，要么全部成功，要么全部失败。如果失败会回滚到事务开始前的状态。
-   一致性（Consistency）：事务操作前后需要满足完整性约束，数据库保持一致性状态。
-   隔离性（Isolation）：数据库允许多个并发事务对数据进行操作，隔离性可以防止多个并发事务因并发执行而产生数据不一致问题。因为多个事务执行相同数据时，不会相互干扰，每个事务都有一个完整的数据，对其他事务是隔离的。
-   持久性（Durability）：事务执行结束后，对数据的操作是持久性的。

​  

我们上面提到在MySQL中，InnoDB引擎是支持事务的，所以它就应该满足事务的特性（ACID）：

-   原子性通过undo log来保证
-   隔离性通过MVCC（多版本并发控制）和锁机制来保证
-   持久性通过redo log来保证
-   一致性通过持久性+原子性+隔离性来一起保证

​  

## 隔离性和隔离级别

当数据库有多个事务同时执行的时候，就可能出现脏读、不可重复读、幻读等问题：

-   脏读：一个事务读到另一个未提交事务的数据，就意味着发生了脏读。
-   不可重复读：一个事务内多次读取同一个数据，如果出现不一致情况，就意味着发生了不可重复读。
-   幻读：一个事务内多次查询某个符合条件的记录数量，如果出现前后两次查询的记录数量不一致，就意味着出现了幻读。

​  

为了解决上面的问题，就有了`隔离级别`的概念。

​  

隔离级别是一柄双刃剑，当隔离级别严的时候，效率就会低。因此，很多时候我们都要去寻找两者之间的平衡点。

​  

SQL标准的事务隔离级别包括以下四种：

-   **读未提交**：一个事务还没提交时，它做的变更就能被别的事务看到。
-   **读提交**：一个事务提交过后哦，它做的变更才能被别的事务看到。
-   **可重复读**：一个事务在执行过程中看到的数据，总是跟这个事务在启动时看到的数据是一致的 。同时，在该隔离级别下，未提交的变更对其他事务是不可见的。
-   **串行化**：对同一行记录，写会加写锁，读会加读锁。当出现读写锁冲突的时候，后访问的事务必须等前一个事务执行完成，才能继续执行。

​  

不同的隔离级别，并发事务时可能发生的问题也不一样。

![image.png](assets/数据库/事务隔离/事务隔离-1.png)

  

对于MySQL来说，默认采用的是`可重复读`隔离级别，也就是在默认的隔离级别下，不会出现脏读和不可重复读的问题，但是还可能出现幻读的问题。

​  

为了在最大程度上解决幻读的问题，MySQL提供以下两种解决方案：

-   针对快照读（普通select），通过MVCC解决幻读。因为在可重复读隔离级别下，一个事务执行过程中看到的数据和事务启动时看到的数据是一致的，即使其他事务在中途插入了数据，对该事务也是不可见的，可以很好的避免幻读的问题。
-   针对当前读（select ... for update 语句），通过next-key lock（记录锁+间隙锁）方式来解决幻读。当执行select ... for update语句的时候会加上next-key lock，如果其他事务操作的数据在next-key lock范围内，会阻塞，无法进行数据操作，可以很好的避免幻读问题。

​  

下面，我们通过一个例子来说明这个四个隔离级别。

​  

现在有一张数据表T，里面有一行数据的值为1，现在启动两个事务A和B，其中A对数据进行查询操作，B对数据进行更新操作，下面是按时间顺序执行的两个事务，针对不同的隔离级别，读取到的V1、V2、V3的值有什么不同。

​  

![image.png](assets/数据库/事务隔离/事务隔离-2.png)

  

-   **读未提交**：V1、V2、V3的值都是2。在读未提交隔离级别下，当事务B将值修改为2时，虽然没有提交事务，但是其他事务都能读到最新的值，所以获取到的值都是2。
-   **读提交**：V1是1，V2、V3是2。在读提交隔离级别下，只有当事务B执行完成后，事务A才能看到事务B所操作的数据结果，所以V2、V3读到的值是2，V1由于在事务B提交之前，所以读到的值是1。
-   **可重复读**：V1、V2是1，V3是2。在可重复读隔离级别下，事务A在提交之前读到的时候都是它在启动事务时候的数据，跟其他事务没有关系，所以V1、V2的值是1，V3因为是在事务A提交之后进行的查询，所以其值是2。
-   **串行化**：V1、V2是1，V3是2。在串行化隔离级别下，事务A会加读锁，事务B会加写锁，读写锁冲突就会导致事务B一直被锁住，直到事务A提交之后，事务B实际是在事务A提交之后才会执行，所以V1、V2的值都是1，V3是2。

​  

在实现上，数据库里面会创建一个视图，访问的时候以视图的逻辑结果为准。

-   在可重复读隔离级别下，这个视图是在事务启动的时候创建的，整个事务期间使用的都是这个视图。
-   在读提交隔离级别下，这个视图是在每个SQL语句开始执行的时候创建的。
-   读未提交隔离级别下直接返回记录的最新值，没有视图的概念，而在串行化隔离级别下是通过锁的方式来避免并行访问的。

​  

可以看到，在不同的隔离级别下，数据库的行为是不同的，而且不同的数据库的隔离级别实现上也有些差异，在实际工作中，根据自身的业务情况进行合理选择。

​  

## 事务隔离的实现

上面介绍了事务的隔离级别，那它们具体是怎么实现的呢？这里展开说明可重复读这种事务。

​  

### Read View是如何工作的

在MVCC（Multi-Version Concurrency Control，多版本并发控制）中，每个事务看到的数据版本是不同的。而为了保证读取的数据版本是符合当前事务隔离级别要求的，数据库需要维护一个“Read View”。

​  

Read View 是指一个时间戳及其对应的有效的、可见的数据版本集合。当一个事务开始执行时，它会获取一个 Read View，并将这个时间戳保存在自己的上下文中。在查询数据时，事务会使用自己保存的时间戳来确定可以看到哪些数据版本。如果一个数据版本的创建时间晚于这个时间戳，则该版本对当前事务不可见。

​  

当其他事务提交更改时，它们可能会产生一些新版本的数据。为了确保每个事务都能看到自己启动时已经存在的所有数据版本，数据库会维护一个全局的读时间戳。当一个事务获得 Read View 时，它会使用当前的读时间戳作为自己的时间戳，并将读时间戳加一。这样，在之后的查询中，该事务就只能看到那些在它启动时已经存在的数据版本，而无法看到后续提交的新版本，这样可以保证事务的一致性和隔离性。

​  

![image.png](assets/数据库/事务隔离/事务隔离-3.png)

​  

Read View 有四个重要的字段：

-   m\_ids ：指的是在创建 Read View 时，当前数据库中「活跃事务」的事务 id 列表，注意是一个列表，“活跃事务”指的就是，启动了但还没提交的事务。
-   min\_trx\_id ：指的是在创建 Read View 时，当前数据库中「活跃事务」中事务 id 最小的事务，也就是 m\_ids 的最小值。
-   max\_trx\_id ：这个并不是 m\_ids 的最大值，而是创建 Read View 时当前数据库中应该给下一个事务的 id 值，也就是全局事务中最大的事务 id 值 + 1；
-   creator\_trx\_id ：指的是创建该 Read View 的事务的事务 id。

​  

除此之外，对于使用 InnoDB 存储引擎的数据库表，它的聚簇索引记录中都包含下面两个隐藏列：

-   trx\_id，当一个事务对某条聚簇索引记录进行改动时，就会把该事务的事务 id 记录在 trx\_id 隐藏列里；
-   roll\_pointer，每次对某条聚簇索引记录进行改动时，都会把旧版本的记录写入到 undo 日志中，然后这个隐藏列是个指针，指向每一个旧版本记录，于是就可以通过它找到修改前的记录。

​  

### 可重复读是怎么工作的

可重复读隔离级别是在事务启动的时候生成一个视图（Read View），然后整个事务都在这个视图中执行。

​  

在可重复读隔离级别下，当一个事务开始时，数据库会为该事务创建一个独立的事务快照，该快照包含了事务开始时数据库中的所有数据，并在整个事务过程中都使用这个快照来提供一致性的数据视图。因此，在该事务执行期间，其他并发事务对数据的更新操作不会影响到当前事务所看到的数据，从而保证了多个数据查询操作返回的结果保持一致，即实现了可重复读的效果。

​  

假设有一个银行账户表，包含用户ID和余额两个字段。

以下是一个示例：

| User ID | Balance |
| --- | --- |
| 1 | 1000 |

现在，假设有两个并发事务，分别是T1和T2。T2想要查询用户1的余额，并执行一些操作，而T1想要将用户1的余额从1000改为1200。

​  

时间线如下：

1.  启动T1事务
2.  启动T2事务
3.  T2查询用于1的余额为1000
4.  T1修改用户1的余额为1200
5.  T2查询用户1的余额为1000
6.  T1提交事务
7.  T2查询用户1的余额为1000
8.  T2提交事务
9.  查询用户1的余额为1200

​  

依据Read View的工作原理，事务T1和T2在启动后会生成对应的ID，如下：

![image.png](assets/数据库/事务隔离/事务隔离-4.png)

​  

事务T2第一次查询用户1的余额的时候，在找到记录后，会先看该记录的trx\_id，发现trx\_id为49，比T2的min\_trx\_id（50）还要小，表示余额为1000的数据是事务T1启动时的最新数据，可以获取这条数据。

​  

接着事务T1执行更新操作，余额从1000变成1200，但是事务未提交，这时候MySQL会记录Undo log，并且和最新的数据建立连接关系，如下：

![image.png](assets/数据库/事务隔离/事务隔离-5.png)

你可以在上图的记录的字段看到，由于事务 T1 修改了该记录，以前的记录就变成旧版本记录了，于是最新记录和旧版本记录通过链表的方式串起来，而且最新记录的 trx\_id 是事务 T1 的事务 id（trx\_id = 50）。

​  

然后事务T2再次去查询数据，发现记录的trx\_id是50，在事务T2的min\_trx\_id和max\_trx\_id之间，然后判断trx\_id是否在m\_ids内，从图中可以看到trx\_id是在m\_ids中的，则表示这条记录是还未提交事务修改的，事务T2不会读取当前的版本，而是通过undo log找到旧版本的记录，直到找到trx\_id小于事务B的min\_trx\_id的值的记录，所以事务T2读取的记录还是trx\_id为49的记录。

​  

当事务T1提交后，由于隔离级别是可重复读，事务T2再次读取记录时，还是基于启动事务T2时创建的Read View来判断当前版本的记录是否可见，所以即使T1提交了事务，T2看到的记录还是trx\_id为49的记录，也就是余额是1000。只有当事务T2提交过后，再次查询就可以查到余额为1200的最新数据。

​  

就是通过这样的方式实现了，**可重复读隔离**级别下在事务期间读到的记录都是事务启动前的记录。

​  

**读提交隔离**和**可重复读隔离**整体思路差不多，只不过读提交是每次读数据的时候都会重新创建Read View，所以多次读取同一数据，可能出现前后两次数据不一致的问题。

​  

## 总结

事务是在 MySQL 引擎层实现的，我们常见的 InnoDB 引擎是支持事务的，事务的四大特性是原子性、一致性、隔离性、持久性，我们这次主要讲的是隔离性。

​  

当多个事务并发执行的时候，会引发脏读、不可重复读、幻读这些问题，那为了避免这些问题，SQL 提出了四种隔离级别，分别是读未提交、读已提交、可重复读、串行化，InnoDB 引擎的默认隔离级别是可重复读。

​  

对于**读提交**和**可重复读**隔离级别的事务来说，它们是通过 Read View 来实现的，它们的区别在于创建 Read View 的时机不同：

-   **读提交隔离**级别是在每个 select 都会生成一个新的 Read View，也意味着，事务期间的多次读取同一条数据，前后两次读的数据可能会出现不一致，因为可能这期间另外一个事务修改了该记录，并提交了事务。
-   **可重复读隔离**级别是启动事务时生成一个 Read View，然后整个事务期间都在用这个 Read View，这样就保证了在事务期间读到的数据都是事务启动前的记录。
