# Linux 软件包、仓库与补丁治理

## 补丁发布流程

先在同发行版、同内核和同硬件型号的 canary 节点执行；验证启动、网络、存储、容器运行时、证书和业务合成探针后再扩大批次。记录未能重启的节点、重启原因和旧内核/旧包的回退路径。

仓库异常时区分 DNS/TLS、签名、元数据过期、镜像同步延迟和依赖冲突。禁止使用未审计的 `--nogpgcheck` 或混用不同发行版仓库；紧急离线包也要保存来源、hash、审批和过期时间。

## 包管理边界

软件包管理器维护依赖、签名和文件归属。生产主机使用受控仓库和固定版本策略，避免从未知 URL 安装二进制。应用依赖与系统依赖分开管理，升级前生成变更清单。

```bash
dnf repolist; dnf updateinfo list security; rpm -qf /usr/bin/sshd; rpm -V openssh-server; apt-cache policy openssh-server
```

内部镜像应通过 TLS、签名校验、访问控制和缓存审计；离线环境使用经过校验的仓库快照。不要为解决一次依赖冲突永久关闭 GPG 检查，应定位版本冲突并形成例外记录。

按漏洞严重性、暴露面、可利用性和业务窗口排序。内核、glibc、OpenSSL、容器运行时和 SSH 属于高影响组件；升级后检查 ABI、服务重启、证书、连接和监控。补丁工单记录前后版本、依赖变化、重启需求、健康探针、异常日志和回滚结果。
