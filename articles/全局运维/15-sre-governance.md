# 全局运维治理：Ansible/IaC、SLO、容量、变更与灾难恢复

## 1. IaC 与配置治理

Ansible/Terraform 等 IaC 的核心是幂等、评审和状态可追踪。仓库按环境分层，变量与秘密分离，模块只负责一个清晰的资源边界；生产执行使用锁、审批和最小凭证，禁止在主机上手改后不回写代码。

```yaml
- hosts: web
  become: true
  serial: 10%
  max_fail_percentage: 0
  tasks:
    - name: Ensure nginx is configured
      ansible.builtin.template:
        src: nginx.conf.j2
        dest: /etc/nginx/nginx.conf
        owner: root
        mode: '0644'
        validate: 'nginx -t -c %s'
      notify: Reload nginx
```

变更前保存基线、影响评估、依赖和回滚条件；变更中分批、可观测、可暂停；变更后做业务探针和配置漂移检查。紧急变更也要补齐记录和复盘，不以“先改了再说”替代治理。

## 2. SLI/SLO、错误预算与容量

SLI 应从用户视角定义：成功率、可用性、端到端延迟、数据新鲜度和恢复时长。SLO 是目标，不是监控阈值；错误预算用于决定发布速度和稳定性投入。容量规划把业务增长、峰值系数、冗余、故障降级和扩容提前时间纳入模型。

```text
可用性 SLI = 成功业务请求数 / 有效业务请求总数
P99 延迟 = 在目标时间窗内 99% 请求完成时间
错误预算 = 1 - SLO
```

容量模型至少覆盖 CPU、内存、磁盘 IOPS/容量、网络、连接数、队列和人工操作窗口；以峰值压测、历史趋势和故障余量校准，不能只按平均值扩容。

## 3. 应急响应与灾难恢复

事件分级依据用户影响、数据风险和扩散速度。指挥官负责决策，执行者负责操作，记录者维护时间线，沟通者同步状态。止损动作包括暂停发布、限流、隔离节点、切换只读和启用降级；每个动作都必须有停止条件。

灾备设计区分备份、复制和故障转移：备份解决误删与回溯，复制降低 RPO，故障转移降低 RTO，但都会引入一致性、成本和操作风险。恢复演练要从空白环境开始，验证 DNS/VIP、证书、权限、依赖、数据和业务写入，而不是只看服务进程启动。

## 4. 安全合规与持续改进

资产、账号、密钥、漏洞、日志、变更和供应链均应有生命周期；高权限访问使用短期授权、MFA、堡垒机和审计。日志最小化采集但满足调查，敏感字段脱敏并设置保留与删除证明。合规控制要映射到实际证据：谁在何时以何权限做了什么、结果是什么、如何回滚。

复盘采用无责原则，输出触发条件、根因、检测缺口、缓解动作、长期修复、负责人和截止日期，并将动作转化为自动化测试、告警或 IaC 规则。没有关闭验证的改进项不算完成。

## 验收标准

- 每项生产服务有 SLI/SLO、负责人、容量模型和故障 runbook。
- 变更可审计、可暂停、可回滚，配置漂移能被发现。
- 关键系统完成备份恢复和跨故障域灾备演练，RTO/RPO 有实测数据。
- 高权限、密钥、漏洞、日志和供应链控制均有证据与复核周期。

## 5. 运行手册与成熟度评估

每个 runbook 都应写清触发信号、前置权限、只读诊断、止损动作、验证探针、回滚条件、升级路径和清理步骤，并在无生产权限的演练环境定期执行。成熟度评估从“靠个人经验”向“有标准流程、自动验证、可量化目标、持续演练”推进；任何自动化都必须保留人工停止开关。

## 6. 变更失败率与学习闭环

按服务统计变更失败率和恢复时间，区分代码、配置、基础设施、容量和第三方依赖。高失败率不等于禁止变更，而是推动更小批次、更强 canary、更快回滚和更完整的测试。复盘动作应回写到 IaC 校验、CI 门禁、Zabbix/日志规则或灾备脚本，并在下一次演练中验证已关闭。

治理的最终证据是可重复执行：新成员按文档能完成部署和回滚，审计者能从提交追溯到审批与运行结果，值班人员能在压力下按 runbook 恢复服务。若只能由原作者口头解释，就仍然存在单点风险。
