# ZooKeeper quorum、选主、滚动升级与恢复

## 1. Quorum 与选主

ZooKeeper 通过多数派 quorum 提交事务；三节点可容忍一台故障，五节点可容忍两台，但网络分区时少数派不可写。节点 ID、投票端口和领导者端口必须稳定且跨故障域。

```bash
echo ruok | nc zk-1 2181; echo mntr | nc zk-1 2181
```

关注 `zk_server_state`、延迟、连接数、未完成请求和磁盘 fsync。客户端连接串必须包含多个节点并设置 session timeout，业务要处理会话重连和临时节点丢失。

## 2. 数据目录与备份

`dataDir` 保存快照，`dataLogDir` 保存事务日志；二者应使用低延迟、独立磁盘。备份不能只复制在线目录，应使用一致性快照并记录 zxid、版本和校验值。

## 3. 滚动升级

一次只升级一个节点，确保 quorum、leader 选举和客户端重连正常；升级前验证兼容矩阵、配置差异、JVM 和磁盘空间。禁止同时重启过半节点。

## 4. 恢复演练

模拟 leader 故障、网络分区、磁盘满、快照损坏和节点重建。恢复时先隔离故障节点，确认其数据版本，再按官方流程清理/同步；不要直接复制另一台 dataDir 覆盖在线目录。验收临时节点、顺序一致性、watch 重建和业务锁。


## 一致性排查

客户端看到 `CONNECTIONLOSS` 时不能直接重试非幂等写入；先用事务 ID 或版本号判断提交状态。`SESSIONEXPIRED` 后临时节点和 watcher 会丢失，应用必须重新创建并重新注册。锁服务要设置过期和 fencing token，避免旧会话继续持有业务锁。

磁盘延迟会直接拖慢 quorum 提交，监控 fsync、事务日志大小、快照间隔和 JVM GC。数据目录不得放在会被自动清理的临时盘；快照保留数量与恢复时间要平衡。

滚动升级后记录每个节点版本、角色、zxid、连接数和客户端错误率。若升级导致 quorum 或客户端协议异常，立即停止后续节点并按兼容版本回退；不要让混合版本长期运行。
