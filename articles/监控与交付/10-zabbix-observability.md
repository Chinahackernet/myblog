# Zabbix 企业监控：Agent/Proxy、主动模式、模板与容量告警

## 1. 监控模型与标签

Zabbix 监控对象由 Host、Interface、Item、Trigger、Template、Discovery 和 Action 组成。先建立服务目录、环境/地域/业务/负责人标签，再设计指标；没有归属、严重度和恢复条件的告警只会制造噪声。

Agent 被动模式由 Server/Proxy 拉取，主动模式由 Agent 主动连接并按配置发送，适合 NAT、短连接或不允许入站的网络。Proxy 承担采集缓冲和故障域隔离，但会增加数据库与队列容量要求。

```ini
# zabbix_agentd.conf（主动模式关键项）
Server=10.50.0.10
ServerActive=10.50.0.10:10051
Hostname=ops-node-01
RefreshActiveChecks=60
AllowKey=system.run[/usr/local/bin/check_*,*]
```

## 2. 模板、发现与自定义指标

模板按“基础 OS—中间件—业务服务”分层，使用宏管理端口、阈值和路径。自定义脚本必须固定输出格式、超时、退出码和权限，拒绝任意用户输入；复杂指标优先用低级自动发现（LLD）批量生成。

```bash
zabbix_agent2 -t vfs.fs.size[/,pused]
zabbix_get -s 10.50.0.21 -k agent.ping
```

监控 Redis/MySQL/Memcached 时同时采集可用性、容量、延迟、错误、复制/集群状态和业务计数。不要只监控端口；例如 MySQL 端口可连但已只读、线程耗尽或复制中断，业务仍然不可用。

## 3. Trigger、通知与容量

Trigger 使用依赖、恢复表达式、持续时间和抑制关系避免抖动。容量告警采用趋势预测和水位分级：预警、行动、保护；每个阈值都要绑定负责人、预计耗尽时间和扩容 runbook。邮件、短信、Webhook 需区分紧急程度，告警内容包含主机、指标、当前值、开始时间、影响、链接和建议动作。

```text
触发：磁盘 pused > 80% 持续 10m
行动：> 90% 自动创建工单并暂停大文件任务
保护：> 95% 摘除节点、只读或扩容
恢复：< 75% 持续 15m 且业务探针通过
```

## 4. 高可用、保留与安全

Server 数据库、Proxy 本地队列和前端应分别规划容量。监控自身也要被监控：队列、history/trends 写入延迟、poller 忙碌度、数据库锁和通知失败。Agent 到 Server 使用 TLS PSK/证书，禁止把 `system.run[*]` 开放给普通主机；脚本输出脱敏并设留存期限。

## 验收与演练

演练主动 Agent 断网、Proxy 磁盘满、数据库延迟、邮件服务不可达、自定义脚本超时、Redis/MySQL 复制异常和磁盘预测告警。验收包括告警产生/恢复时延、重复抑制、通知路由、容量预测准确度和 runbook 可执行性。

## 5. 监控规模与数据保留

容量估算需要把主机数、每主机 item 数、采集间隔、历史/趋势保留和 LLD 发现增长纳入模型。提高采集频率会同时增加 Agent、Proxy、Server poller 和数据库写入压力；优先用依赖项、预处理和趋势数据降低基数。数据库维护窗口要验证 housekeeper、分区/归档和索引膨胀，避免清理任务与告警高峰争抢 I/O。

## 6. 告警质量复盘

每次重大事件复盘“是否提前发现、是否正确分派、是否能直接执行 runbook、恢复告警是否可靠”。对重复告警、无动作告警和长期未确认告警设置淘汰规则；任何自动化修复都要有最大重试次数、幂等检查和人工接管入口。

模板发布也应走版本化流程：在测试主机导入并验证表达式，再小批量绑定生产主机，观察 item 采集耗时、触发器数量和数据库写入增量，确认无误后才扩大范围。

对业务指标使用低基数标签；将用户 ID、订单号等高基数字段留在日志或链路系统，避免 Zabbix history 表和前端聚合被无界基数拖垮。
