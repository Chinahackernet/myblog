# 故障应急响应流程（Incident Response Runbook）

> 版本：v1.0 ｜ 适用：AI Agent 六维自动化生态 + 内容创作业务 ｜ 维护人：Adam（SRE 辅助）
> 原则：**先止血，后定位；免责文化；每条动作可执行、有时间戳、有人负责。**

---

## 1. 目标与适用范围

**目标**：把故障从"发现到恢复"的时间（MTTR）压到可控范围——
- P0：30 分钟内恢复
- P1：2 小时内恢复
- 故障复盘行动项 90% 在承诺期限内闭环

**适用场景**（本生态常见故障形态）：

| # | 故障形态 | 示例 |
|---|---------|------|
| 1 | 内容平台 API 故障 | 平台限流/封号/接口变更导致发布任务全挂 |
| 2 | Agent 工作流故障 | 编排任务卡死、循环重试、产出错误内容 |
| 3 | 模型/第三方 API 依赖故障 | LLM API 超时、Key 额度耗尽、账单异常 |
| 4 | 基础设施故障 | 服务器宕机、数据库/队列积压、磁盘满 |
| 5 | 数据管道故障 | 采集→处理→分发链路中断、数据错乱 |
| 6 | 安全事件 | 账号被盗、API Key 泄露、内容被恶意篡改 |

---

## 2. 角色与职责（单人/小团队版）

角色可以一人身兼多职，但**职责必须分离清晰**，避免"又开车又看地图"：

| 角色 | 职责 | 单人时 |
|------|------|--------|
| **IC（Incident Commander，总指挥）** | 唯一决策人：定级、分配任务、宣布缓解/恢复 | 默认由**发现人**担任 |
| **操作员（Operator）** | 执行止血动作：回滚、限流、重启、kill 任务 | IC 自己 |
| **沟通员（Comms）** | 维护时间线、发状态更新、对外沟通 | 记录必须做！哪怕只有自己 |
| **记录员（Scribe）** | 时间线日志：谁、何时、做了什么、结果如何 | 同上，与操作合流 |

**升级规则**：
- 故障 30 分钟未缓解 → 自动升级一级（P1→P0），并拉更高决策权的人（如合伙人/技术顾问）。
- IC 判定自己"陷进去"（在钻技术细节超过 10 分钟）→ 立即移交指挥权给第二人，自己转操作员。

---

## 3. 故障分级（P0–P3）

| 级别 | 定义 | 首次响应 | 缓解目标 | 示例 |
|------|------|---------|---------|------|
| **P0** | 核心业务完全不可用 / 资损 / 安全事故 / 影响 >50% 用户 | ≤15 分钟 | ≤30 分钟 | 所有平台发布全挂；API Key 泄露；账号被盗 |
| **P1** | 核心业务严重降级 / 影响 10–50% 用户 | ≤30 分钟 | ≤2 小时 | 小红书/公众号批量发布失败；Agent 主链路卡死 |
| **P2** | 非核心功能故障，有 workaround | ≤4 小时 | 当日 | 某个平台的数据统计不准；次要 Agent 任务失败 |
| **P3** | 有影响但不紧急 / 噪音级 | 下个工作日 | — | 监控面板缺数据；日志有少量报错 |

**定级判断顺序**：是否资损/安全 → 是否核心链路 → 影响用户比例 → 有无临时绕过方案。

## 4. 应急响应全流程

```
检测 → 定级 → 响应启动 → 止血缓解 → 恢复确认 → 复盘闭环
```

### 4.1 检测（Detection）
故障入口按优先级：
1. **告警**（自动）：监控触发 → 进告警群
2. **用户/粉丝反馈**：内容没发、发了错的 → 客服/私信渠道
3. **主动巡检**：定时健康检查（Agent 心跳、任务队列深度、平台 API 配额余量）
4. **被动发现**：刷到异常内容、财报式数据异常

> 要求：**每条告警必须能回答"影响了什么用户、什么功能"**，否则是噪音，不该建。

### 4.2 定级 + 响应启动（15 分钟内完成）
IC 确认后立刻执行 3 件事（缺一不可）：
1. **宣布故障**：在告警/协作群发启动通告（模板见 §6.1），@ 干系人
2. **开时间线**：建一份共享时间线文档（模板见 §7），此后所有动作带时间戳记录
3. **设闹钟**：15 分钟一次状态确认；超过分级缓解目标时间未解决 → 触发升级规则

### 4.3 止血缓解（Stabilize）— 先止血，后定位
**止血动作优先级（按此顺序尝试，不要跳）**：

| 优先级 | 动作 | 适用场景 |
|-------|------|---------|
| 1 | **回滚（Rollback）** | 最近有发布/配置变更 → 回滚到上一已知良好版本 |
| 2 | **限流/熔断** | 第三方 API 限流、系统过载 → 降速、熔断重试风暴 |
| 3 | **降级（Degrade）** | 核心链路依赖挂 → 关掉非核心功能保核心 |
| 4 | **扩容/清积压** | 队列积压、资源饱和 → 加并发实例或临时清队列 |
| 5 | **热修复** | 以上都不行才改代码 → 必须走最小改动 + 快速验证 |

**铁律**：
- 故障中**禁止**做架构级改动、大范围重构、顺手修无关 bug。
- 每做一步缓解，30 秒内确认效果（指标是否回落），无效立即换下一招，不要恋战。
- 若 20 分钟内找不到头绪 → 停止深挖，先按"最近变更回滚"处理（90% 故障源于变更）。

### 4.4 恢复确认（Recovery）
缓解动作生效 ≠ 故障结束。恢复必须满足：
- ✅ 核心指标回到基线（错误率、延迟、队列深度）
- ✅ 持续观察 ≥ 15 分钟无反弹
- ✅ 积压任务消化完毕（发布队列追平）
- ✅ 数据一致性核对（没有发重复/发错内容，有则补发/撤回）

确认后 IC 宣布**解除故障状态**，发解除通告（§6.3）。

### 4.5 复盘闭环（Postmortem）
P0/P1 **必须**在 72 小时内出复盘；P2/P3 可合并月度复盘。
流程：5-Why 根因分析 → 行动项清单（每条：责任人 + 期限 + 优先级）→ 追踪闭环 → 沉淀进 Runbook/自动检查。

## 5. 沟通规范

**节奏铁律**：
- 启动通告后，**每 15–30 分钟**发一次状态更新（即使没有新进展，也要发"仍在定位中"）
- 对外（用户/粉丝）口径统一由 IC/沟通员发出，**操作员不对外发言**
- 所有更新使用模板，控制信息密度，禁止技术黑话对外

**三类沟通对象**：
| 对象 | 内容 | 频率 |
|------|------|------|
| 内部群（自己/团队/顾问） | 技术细节、时间线、猜测 | 15–30 min |
| 干系人（合伙人/大客户） | 影响范围、预计恢复时间 | 30–60 min |
| 对外（用户/粉丝） | 简洁致歉 + 状态 + 恢复通知 | 仅启动/重大变化/恢复 3 次 |

---

## 6. 沟通模板

### 6.1 故障启动通告（内部）
```
🚨 [P0] 故障启动 | <服务名> <简述症状>

- 影响：<影响的功能>，约 <X%> 用户/账号
- 发现时间：<HH:MM>
- 当前状态：<正在止血/正在定位>
- IC：<人名> ｜ 操作员：<人名>
- 时间线：<链接>
- 下次更新：<HH:MM>
```

### 6.2 状态更新（内部）
```
⏱ [P0] 更新 <N> ｜ <HH:MM> ｜ 已持续 <X> 分钟

- 进展：<做了什么，结果>
- 当前假设：<正在排查的方向>
- 影响变化：<扩大/收窄/不变>
- 预计恢复：<时间或"尚不确定">
```

### 6.3 故障解除通告（内部 + 对外精简版）
```
✅ [P0] 解除 | <服务名>

- 恢复时间：<HH:MM>（故障持续 <X> 分钟）
- 根因（初步）：<一句话>
- 已执行：<止血措施>
- 后续：<72h 内出复盘报告 + 行动项>
- 感谢：<参与人>
```

### 6.4 对外（用户/粉丝）模板
```
【服务异常说明】
<时间> 起，<什么功能>出现异常，影响部分用户。已定位到<原因类别>，
正在处理中。<预计时间> 前恢复。给您的使用带来不便，非常抱歉。

【已恢复通知】
<功能>已恢复正常。本次为<原因>所致，我们已<措施>，避免再次发生。再次致歉。
```

## 8. 故障场景速查（本生态预置 Runbook 骨架）

| 场景 | 症状信号 | 止血动作 | 恢复检查 |
|------|---------|---------|---------|
| **平台限流/封号** | 单平台错误率陡增、403/429 密集 | 停该平台任务 → 备用账号/备用通道 → 降速 | 小流量试发 1 条 → 观察 15min |
| **LLM API 故障** | 全 Agent 任务超时、成本突增 | 切换备用模型/Key → 熔断重试 → 降级为模板输出 | 单任务验证 → 恢复队列 |
| **Agent 工作流卡死** | 队列深度只增不减、心跳丢失 | kill 卡死任务 → 检查循环条件 → 重置游标 | 队列追平 → 数据无重复 |
| **内容发错/发重复** | 用户反馈、内容抽查异常 | 立即撤回/隐藏 → 暂停该 Agent → 核对数据源 | 全量核对受影响内容 |
| **数据库/队列积压** | 延迟指标飙升、磁盘/连接告警 | 限流入口 → 扩连接/扩实例 → 必要时清积压 | 延迟回落基线 |
| **Key/账号泄露** | 异常调用、账单异常、异地登录 | **轮换 Key/改密（最高优先）** → 查调用日志 → 审计 | 确认无残留访问 |

> 每条告警必须有对应 Runbook 的链接，否则不算可操作告警。

## 9. 演练与持续改进

- **季度故障演练**：每季度挑 1 个高频故障形态（如"平台 API 全挂"）做桌面推演，走完整流程，计时。目标：P0 流程 ≤ 20 分钟走完。
- **混沌测试**（可选）：在测试环境注入故障（断网、Key 失效、队列暴涨），验证自动降级是否生效。
- **复盘行动项闭环**：每周花 10 分钟检查复盘行动项进度，超期未完成 → 上升为待办 P1。
- **流程本身要迭代**：每次复盘最后问一句"响应流程哪里卡了？"——流程问题也是根因的一部分。

---

## 10. 关键度量（写在最后，用来证明流程有效）

| 指标 | 含义 | 目标 |
|------|------|------|
| MTTD | 平均发现时间 | < 5 分钟（靠告警，不靠人发现） |
| MTTR | 平均恢复时间 | P0 < 30min，P1 < 2h |
| 告警精确率 | 有真实影响的告警占比 | > 90%（否则是噪音，调规则） |
| 复盘按时完成率 | 72h 内出复盘 | 100%（P0/P1） |
| 行动项闭环率 | 期限内完成 | > 90% |
| 重复故障率 | 同一根因再发 | 0（有复盘就该杜绝复发） |

## 附：启动前 Checklist（现在就做，不用等故障）

- [ ] 建好**告警/协作群**（内部 + 干系人），确认 @ 全员可用
- [ ] 建好**对外公告渠道**（公众号/群公告的发布权限与文案口径）
- [ ] 把 §6 模板 + §7 时间线模板存到常用位置（文档/Notion/飞书）
- [ ] 核心服务每项至少 1 条**真实告警**（不是日志噪音）
- [ ] 高频故障形态（§8）每项至少 1 条**已写好的止血动作**
- [ ] 确定**备用通道**：备用平台账号、备用模型 Key、备用发布通道
- [ ] 给 Key/账号的**轮换流程**写好（泄露时 5 分钟内能执行）
- [ ] 定好升级联系人：谁是"故障 30 分钟没解决时该打电话的人"

> 流程的价值不在文档，在于**第一次真实故障时照着走一遍**。建议下周先做一次 20 分钟的桌面演练。
